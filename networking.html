Networking

Zero-Trust Network Architecture

Microsoft Fabric is a SaaS platform, but enterprises still need strict network boundaries. Here's how to integrate Fabric into your corporate zero-trust posture.

💡 Key Principle

Zero-trust means never trust, always verify. All traffic between users, Fabric, and data sources should traverse private channels — disable public endpoints wherever possible.

🔒 Inbound — Users to Fabric

Control how users and applications connect to Fabric workspaces and services.

  • Azure Private Link — Route all user traffic through private endpoints in your VNet
  • Conditional Access — Entra ID policies enforce device compliance, location, MFA
  • Tenant restrictions — Prevent data exfiltration to unauthorized tenants

🔗 Outbound — Fabric to Data

Control how Fabric connects to your private data sources and external services.

  • Managed Private Endpoints — Fabric connects to your resources through Azure backbone, not public internet
  • VNet Data Gateways — Bridge Fabric to on-premises or VNet-isolated resources
  • Trusted Workspace Access — Allow firewalled Storage Accounts to trust Fabric

🛡️ Internal — Between Services

Secure communication between Fabric components and Microsoft backbone services.

  • Managed VNets — Spark workloads run in Fabric-managed virtual networks with controlled egress
  • Service tags — NSG rules using DataFactory and PowerBI service tags
  • Data encryption — TLS 1.2+ in transit, Microsoft-managed keys at rest

Inbound

Private Link for Fabric

Route all user and application traffic to Fabric through Azure Private Link — keeping it off the public internet entirely.

How it works

  1. Create a Private Endpoint in your VNet targeting the Microsoft.PowerBI/privateLinkServicesForPowerBI resource provider
  2. Configure Private DNS Zones — resolve *.analysis.windows.net, *.pbidedicated.windows.net, and *.app.powerbi.com to private IPs
  3. Block public access — In the Fabric Admin Portal → Tenant Settings, disable "Azure Private Link" toggle to block public access at tenant level
  4. Test connectivity — Use nslookup or Resolve-DnsName from within the VNet to confirm private resolution
⚠️ DNS is critical

Misconfigured DNS is the #1 cause of Private Link failures. Every client (including on-premises via VPN/ExpressRoute) must resolve Fabric endpoints to their private IP. Use Azure Private DNS Zones linked to the VNet, and configure DNS forwarders for on-premises clients.

PowerShell — Verify private DNS resolution
# From a VM inside the VNet
Resolve-DnsName "yourworkspace.analysis.windows.net"
# Should return a private IP (10.x.x.x), NOT a public IP

# Verify from on-premises (must have DNS forwarder)
nslookup yourworkspace.analysis.windows.net

Outbound

Managed Private Endpoints (MPE)

Secure outbound connections from Fabric to your private data sources — without exposing them to the public internet.

What are Managed Private Endpoints?

When Fabric needs to read from resources that have public access disabled (like ADLS behind a firewall), you create a Managed Private Endpoint from the Fabric workspace. Fabric creates a private endpoint inside its managed VNet, and you approve it in the Azure Portal on the target resource.

Setup Steps

1. Enable Managed VNet

In Fabric workspace settings, enable Managed Virtual Network for Spark workloads. This is a prerequisite for MPE.

2. Create MPE

Workspace Settings → Managed Private Endpoints → + New. Select the target resource type and enter the Azure Resource ID.

3. Approve in Azure

Go to the target resource (e.g., Storage Account) → Networking → Private Endpoint Connections → Approve the pending connection.

4. Use in Notebooks

Connect to the resource from Spark notebooks or pipelines. Traffic flows over Azure backbone via the approved private endpoint.

⚠️ Performance note

When Managed VNet is enabled, Starter Spark pools are not available. Spark session start-up time increases because pre-warmed clusters cannot be used. Plan for capacity accordingly — use F64+ SKUs and consider keeping sessions alive for iterative development.

Isolation

Managed Virtual Networks

Fabric-managed VNets provide network isolation for Spark workloads with controlled outbound access.

How Managed VNets Work

When enabled at the workspace level, Fabric provisions a Microsoft-managed virtual network for all Spark compute in that workspace. Outbound traffic is restricted — Spark can only access destinations through approved Managed Private Endpoints or public endpoints you explicitly allow.

✅ What is controlled

  • All Spark notebook and pipeline outbound traffic
  • Connections to Azure PaaS resources via MPE
  • Egress to public internet (blocked by default)
  • DNS resolution within the managed VNet

⚠️ What is NOT covered

  • SQL endpoint (Warehouse, SQL Analytics) — uses separate connectivity
  • Power BI / semantic models — not in managed VNet
  • Data Factory pipelines — use VNet Data Gateways instead
  • KQL / Eventhouse — separate networking model
💡 Best practice

Enable Managed VNet on workspaces that process sensitive data via Spark. For workspaces doing only Power BI reporting or SQL queries, it's not needed and avoids the Spark startup penalty.

Hybrid

VNet Data Gateways

Connect Fabric to on-premises data sources and VNet-isolated Azure resources without installing software.

When to Use

VNet Data Gateways are the recommended approach when you need Fabric to reach resources inside a VNet that aren't accessible through Managed Private Endpoints — for example, on-premises SQL Server via ExpressRoute, or Azure resources in peered VNets.

VNet Data Gateway

  • No software to install — fully managed by Microsoft
  • Runs in a delegated subnet in your VNet
  • Supports Dataflows Gen2, Semantic Models, Paginated Reports
  • Accesses anything reachable from the subnet (on-prem via peering/ER)

On-Premises Data Gateway (classic)

  • Software installed on a VM or server you manage
  • Required for some legacy connectors
  • Outbound HTTPS — no inbound ports needed
  • Consider only when VNet Data Gateway doesn't support your source

Storage

Trusted Workspace Access

Allow Fabric to access firewalled Azure Storage Accounts using workspace identity — no public access or private endpoints required.

How it works

Azure Storage firewall can be configured to trust specific resource instances. By registering Fabric workspace identities, you allow OneLake shortcuts and Spark to access the storage — even when "Allow public access" is OFF.

Azure CLI — Enable trusted access for a Storage Account
# 1. Get the Fabric workspace identity (ARM resource ID)
#    Found in Workspace Settings → Azure tab

# 2. Add it as a resource instance rule on the Storage Account
az storage account network-rule add \
  --account-name mystorageaccount \
  --resource-group myRG \
  --resource-id "/subscriptions/{sub}/resourceGroups/{rg}/providers/Microsoft.Fabric/workspaces/{workspaceId}" \
  --tenant-id "{tenantId}"

# 3. Verify the Storage Account firewall settings
az storage account show --name mystorageaccount \
  --query "networkRuleSet.resourceAccessRules"
💡 When to use Trusted Access vs MPE

Trusted Workspace Access is simpler for OneLake shortcuts and basic Spark access to ADLS. Managed Private Endpoints are needed for SQL databases, Key Vault, Cosmos DB, and any non-storage resource that requires private connectivity.

Identity

Conditional Access & Tenant Policies

Use Entra ID Conditional Access and Fabric Tenant Settings to enforce who, from where, and how users access Fabric.

📍 Location-Based Policies

  • Block access from non-corporate IP ranges
  • Require VPN/Private Link for sensitive workspaces
  • Geo-fence to specific countries

📱 Device Compliance

  • Require Intune-compliant or Hybrid AD-joined devices
  • Block access from unmanaged/personal devices
  • Enforce app protection policies on mobile

🔑 Authentication Strength

  • Require phishing-resistant MFA (FIDO2, Windows Hello)
  • Step-up authentication for admin operations
  • Session controls (sign-in frequency, persistent browser)

🚫 Tenant Restrictions

  • Prevent users from accessing other organizations' Fabric tenants
  • Block guest access to sensitive workspaces
  • External sharing policies per workspace
🎯 Recommended baseline

At minimum, configure: (1) Require MFA for all Fabric users, (2) Block access from non-compliant devices, (3) Restrict admin portal access to named locations. These three policies prevent the majority of identity-based attacks.
